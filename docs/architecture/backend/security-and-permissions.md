# Security and Permissions

## Authentication

- Staff, platform operators, and learners authenticate through the same endpoint and receive the same token format. There is no separate learner login route, so lockout, throttling, and token issuance are implemented once.
- Every user signs in with a username and a password.
- A learner's username is generated by the system. See the learner username generation rules in `domain-model.md`.
- Phone numbers and email addresses are contact details, not credentials. Neither may be used to sign in.
- Portal access is issued with no password and a pending activation status. The learner sets the password on activation, and the account becomes active only then.
- A login must be refused while the account is not active, including pending activation, suspended, locked, and disabled.
- A login must be refused when the learner behind it is no longer in an active enrollment status. Disabling it must not depend on service code remembering to do so.
- Learner accounts outnumber staff accounts by a wide margin and use self-chosen passwords, so authentication rate limiting is a requirement rather than a hardening step.

## Learner Authority

- A learner's authority over their own record is ownership, not scope.
- Grant it through permissions that end in `-own`, resolved against the login's `learnerId`.
- Do not model this as a further scope level. Scope answers which school or branch a permission covers; ownership answers whose record it covers.
- A role declares whether it is for staff or for learners, and a grant must match the kind of account it lands on. A learner account must never be able to hold a staff role.

## Tenant Isolation

- School is the tenant boundary for authorization.
- Users may access only schools they are authorized for.
- Users may access only branches they are authorized for unless granted school-level permissions.
- Learner data must always be filtered by school authorization.
- A learner belongs to exactly one school and must not be shared across schools.

## Learner Permissions

- Creating a learner requires permission for the target school and initial branch.
- Reading or updating a learner requires permission for the owning school.
- Branch-level users may read or update only learners currently assigned to their authorized branches unless a school-level role grants broader access.

## Branch Transfer Permissions

- Creating a branch transfer request requires permission for the learner's current branch.
- Approving or rejecting a transfer requires permission for the school and, where branch-level approval is enforced, permission over both source and target branches.
- Transfer APIs must verify that the transfer, learner, source branch, and target branch all belong to the requested school.
